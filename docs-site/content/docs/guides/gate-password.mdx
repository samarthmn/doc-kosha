---
title: "Gate a link with a password"
description: "Require a password before a shared document or data room opens, rotate or remove it later, and understand the per-link attempt limit and the one-hour unlock window."
---

A password gate is the simplest control: the viewer must type a shared secret before any content is released.

## Add a password

1. Open the document or data room and go to the **Share** tab.
2. Create a **New Link**, or **Edit** an existing one.
3. Open the **Security** tab.
4. Switch on **Password protection**. The badge next to it changes from `Disabled` to `Enabled`.
5. Type the password in the field below.
6. Save.

The password may be up to 256 characters. DocKosha does not impose a complexity rule, so pick something strong yourself. Send it to your viewers over a different channel than the link.

## Change or remove the password

Reopen the link and go to **Security**:

| You want to               | Do this                                                                                             |
| ------------------------- | --------------------------------------------------------------------------------------------------- |
| Keep the current password | Leave the field blank. It reads _"Leave blank to keep existing password"_ and shows a `Saved` badge |
| Rotate it                 | Type the new password and save. It replaces the old one immediately                                 |
| Remove the gate           | Switch **Password protection** off and save                                                         |

There is no way to read the current password back. It is stored only as a bcrypt hash; the raw value is never kept.

## What the viewer sees

A password-gated document link shows:

> **Password Protected Link** — Enter the password to view the document.

A data-room link shows **Protected Data Room** with an **Unlock Data Room** button.

A wrong password produces _"Incorrect password. Please try again."_ No content, metadata, or file name is released before the password matches.

## How it is enforced

The check happens on the server when the link is resolved, before any document bytes or signed storage URLs are issued. A correct password returns a signed, `httpOnly` access cookie scoped to that specific resource and link.

**That cookie lasts one hour.** Within the hour the viewer can move around without retyping; after it expires the gate is presented again. Clearing cookies or switching to a private window forces the gate immediately — which is how you should test.

## The attempt limit

Password attempts are rate limited **per link**: 30 attempts inside a fixed ten-minute window.

<Callout type="warn" title="Over the limit, a correct password is rejected too">

Once the window's 30 attempts are used, the server answers every further attempt with _"Incorrect password"_ until the window rolls over — including attempts with the right password. The limit is deliberately per link rather than per IP address, so the total number of guesses is bounded no matter how many machines are used. The cost is that a flood of wrong guesses can lock out legitimate viewers for the rest of that window. If a viewer insists their password is correct, have them wait and try again.

</Callout>

## Combining a password with other gates

A link can carry several gates at once, and the viewer must pass all of them. The **Access controls** chips in the link editor's summary panel list what is active.

A password identifies nobody: it is shared knowledge, so it cannot tell you who opened the document. If you need to know that, add [email verification](/docs/guides/gate-email-otp) or an [allowlist](/docs/guides/gate-allow-and-blocklists), or turn on **Collect emails for analytics**.

## Honest limits

- **A shared password is only as private as the people you gave it to.** It cannot stop forwarding. To bind access to individuals, use an allowlist or email verification instead.
- **Passing the gate does not stop copying.** Downloads are off by default; screenshot protection is a best-effort deterrent that no browser can turn into a real block on operating-system screen capture, screen recorders, or a camera. See [Download and screenshot controls](/docs/guides/download-and-screenshot-controls).
- **Password changes do not evict current viewers.** Someone who unlocked the link minutes ago keeps access until their one-hour window ends. To cut access off immediately, delete the link.

## Troubleshooting

| Symptom                                                                  | Cause                                   | Fix                                         |
| ------------------------------------------------------------------------ | --------------------------------------- | ------------------------------------------- |
| Save fails: _"Password is required when password protection is enabled"_ | Toggle on, field empty                  | Type a password or turn the toggle off      |
| The correct password is rejected                                         | The per-link attempt limit is exhausted | Wait for the ten-minute window to roll over |
| A viewer is not asked for the password                                   | They unlocked it within the last hour   | Test in a private window                    |
| You forgot the password                                                  | It is stored only as a hash             | Rotate it by typing a new one               |
